# CONSIDERATIONS.md

## 1. 입력값 정규화

커스텀 확장자는 저장 전에 아래 순서로 정규화한다.

- trim()
- 소문자 변환
- 앞의 '.' 제거
- 영문/숫자만 허용
- 길이(1~20자) 검증

예)

```
.EXE → exe
 Sh → sh
```

애플리케이션에서 정규화를 수행하며, DB에도 `LOWER(extension)` Unique Index를 추가하여 직접 DB 수정이나 예외 상황까지 방어하였다.

---

## 2. 보안 및 검증

모든 검증은 서버에서 수행한다.

### 적용

- 중복 확장자
- 최대 200개
- 길이 제한
- 허용 문자
- 고정 확장자 삭제 금지

### 고려 후 제외

- Magic Number(File Signature) 검사
- Rate Limit
- Audit Log

운영 환경에서는 Apache Tika, Bucket4j 등을 적용하는 것이 바람직하지만 과제 범위를 고려하여 제외하였다.

---

## 3. 파일 업로드 정책

### 확장자 검사

- 마지막 확장자만 검사한다.
- `.env`, `Makefile`처럼 확장자가 없는 파일은 정책 대상에서 제외한다.

### 파일 저장

원본 파일명은 사용하지 않고

```
UUID + 원래 확장자
```

형태로 저장하여 Path Traversal을 방지하였다.

### 파일 크기

Spring Multipart 설정으로 10MB까지 허용한다.

---

## 4. 정책 결정

- 고정 확장자는 삭제할 수 없다.
- 고정 확장자를 커스텀으로 추가할 수도 없다.
- 커스텀 확장자는 최대 200개까지 허용한다.
- 동일한 파일은 별도의 업로드 요청으로 간주한다.

---

## 5. 예외 및 일관성

확장자 추가/삭제는 `@Transactional`로 처리하여 실패 시 롤백한다.

업로드 과정에서 파일 저장 이후 예외가 발생하면 저장된 파일을 삭제하여 파일 시스템과 DB의 불일치를 방지하였다.

---

## 6. 동시성

현재는

```
개수 확인
→ 저장
```

순으로 처리한다.

동시에 여러 요청이 발생하면 일시적으로 200개를 초과할 가능성이 있다.

실제 서비스에서는 Optimistic Lock 또는 SERIALIZABLE Transaction 등을 적용하여 보완할 수 있다.

---

## 7. 운영 환경 고려

- DB 접속 정보는 Environment Variable로 관리
- CORS는 운영 Frontend만 허용
- Docker 기반으로 동일한 실행 환경 보장

정책 변경(추가/삭제)은 즉시 업로드 검사에 반영되도록 구현하였다.

업로드 진행 중 정책이 변경되는 경우에는 **업로드 요청 시점의 정책을 기준으로 처리**하도록 결정하였다.
