# CONSIDERATIONS.md — 기획/보안/예외/운영 고려사항

---

## 1. 확장자 입력값 정규화 정책

### 정책 결정

커스텀 확장자 추가 및 고정 확장자 조회 시, **저장 전 반드시 소문자로 정규화**한다.

구체적으로 아래 순서로 처리한다.

1. 앞뒤 공백 제거 (`strip()`)
2. 소문자 변환 (`toLowerCase()`)
3. 앞의 점(`.`) 제거 — `.sh` 입력 시 `sh`로 저장
4. 영문자·숫자만 허용 — 특수문자, 공백, 유니코드 차단
5. 길이 검증 — 1자 이상, 20자 이하

### 근거

- `EXE`, `Exe`, `exe`는 동일한 확장자다. 대소문자를 구분하면 같은 확장자가 중복 등록되거나 차단 검사에서 누락될 수 있다.
- 파일 업로드 시 확장자 비교도 소문자 기준으로 수행하므로, 저장 시점에 정규화해두면 비교 로직이 단순해진다.

### 구현 위치

- `BlockedExtensionService.normalize()` — 저장 전 호출
- `UploadService.extractExtension()` — 업로드 파일명에서 추출 시 소문자 변환

### DB 레벨 이중 방어

애플리케이션에서 정규화를 보장하지만, DB에서도 함수 기반 유니크 인덱스로 2차 방어한다.

```sql
CREATE UNIQUE INDEX uq_extension_lower ON blocked_extension (LOWER(extension));
```

애플리케이션 버그나 직접 DB 조작으로 대문자 값이 삽입되더라도 중복을 막는다.

## 2. 검증/보안 관점

### 서버 사이드 검증 필수

클라이언트(브라우저) 검증은 우회 가능하다. curl, Postman 등으로 직접 요청을 보내면 클라이언트 검증을 건너뛸 수 있으므로, **모든 검증은 서버에서 수행**한다.

### 확장자 기반 검사의 한계 — 파일 시그니처(매직 넘버)

확장자는 파일명의 일부일 뿐이며, 실제 파일 내용과 다를 수 있다. 예를 들어 `report.jpg`로 이름을 바꾼 실행 파일은 확장자 검사를 통과한다.

**현재 구현**: 확장자 기반 검사만 수행한다.

**고려했으나 제외한 이유**: 파일 시그니처 검증은 Apache Tika 등 라이브러리가 필요하고 구현 복잡도가 높다. 과제 범위를 초과한다고 판단했다. 운영 환경에서는 추가 적용을 권장한다.

### 이중 확장자 처리

`file.exe.txt`처럼 이중 확장자가 있는 경우, **마지막 확장자만 검사**한다.

**근거**: 대부분의 OS와 브라우저가 마지막 확장자를 기준으로 파일 타입을 판단한다. 다만 `file.exe.txt`는 실제로 txt로 열리므로 위험도가 낮다고 판단했다.

**보완 가능한 방향**: 전체 파일명에서 차단 확장자 포함 여부를 검사하는 방식으로 강화할 수 있다. CONSIDERATIONS.md에 기록하고 구현은 제외했다.

### 확장자 없는 파일

확장자가 없는 파일(예: `Makefile`, `.env`)은 **현재 허용**한다.

**근거**: 확장자 없는 파일은 실행 파일일 수도 있지만, 텍스트 파일인 경우가 더 많다. 차단 정책의 기준이 "확장자"이므로 확장자가 없는 파일은 정책 적용 대상 밖으로 판단했다.

### MIME 타입 스푸핑

Content-Type 헤더는 클라이언트가 임의로 설정할 수 있으므로 신뢰하지 않는다. 확장자 기반 검사를 서버에서 수행하는 것으로 대응한다.

### 파일 저장 시 원본 파일명 사용 금지

원본 파일명을 그대로 저장하면 경로 조작(Path Traversal) 공격에 취약하다. 예를 들어 `../../etc/passwd` 같은 파일명이 들어올 수 있다.

**현재 구현**: UUID로 rename 후 저장한다. 원본 파일명은 응답에만 포함한다.

### 파일 크기 제한

`application.properties`에서 10MB로 제한한다.

```properties
spring.servlet.multipart.max-file-size=10MB
spring.servlet.multipart.max-request-size=10MB
```

## 3. 정책/데이터 관점

### 고정 확장자와 커스텀 확장자 중복

고정 확장자(`exe` 등)를 커스텀으로도 추가하려 하면 `DUPLICATE_EXTENSION` 오류를 반환한다. 고정 확장자는 이미 DB에 존재하므로 `uq_extension_lower` 인덱스에서 충돌이 발생한다.

**정책**: 고정 확장자는 커스텀 목록에 표시하지 않고, 커스텀으로 추가도 불가하다.

### 200개 / 20자 제한

- **200개**: 확장자 목록이 지나치게 길어지면 조회 성능과 UX 모두 저하된다. 실무에서 200개 이상의 확장자를 차단하는 경우는 드물다고 판단했다.
- **20자**: 일반적인 확장자는 2~5자이며, 복합 확장자(`tar.gz` 등)를 고려해도 20자면 충분하다.

초과 시 `LIMIT_EXCEEDED` 오류를 반환하고, 클라이언트에서도 카운터로 안내한다.

### 정책 변경 이력(감사 로그)

**고려했으나 제외**: 누가 언제 어떤 확장자를 추가/삭제했는지 이력을 남기는 것은 운영 환경에서 중요하다. 과제 규모상 별도 이력 테이블은 구현하지 않았다. 실제 서비스라면 `extension_audit_log` 테이블을 추가하거나 애플리케이션 로그로 대체할 수 있다.

## 4. UX/예외 관점

### 차단 시 사용자 메시지

차단된 파일 업로드 시 아래 형식으로 응답한다.

```json
{
  "success": false,
  "code": "BLOCKED_EXTENSION",
  "message": "exe 확장자는 업로드가 차단되어 있습니다."
}
```

어떤 확장자가 왜 막혔는지 명확히 전달한다.

### 저장 실패 시 일관성

확장자 추가/삭제는 단일 트랜잭션으로 처리한다. DB 저장 실패 시 화면 상태가 변경되지 않도록 서비스 레이어에서 `@Transactional`로 보장한다.

## 5. 운영 관점

### 로그

차단된 업로드 시도는 `BlockedFileException`이 발생하며, `GlobalExceptionHandler`에서 처리된다. 운영 환경에서는 이 시점에 파일명, IP, 시각을 로그로 남기는 것을 권장한다. 현재는 구현하지 않았다.

### 향후 확장 고려

- **사용자별 정책**: 현재는 전역 정책만 존재한다. 사용자별 정책이 필요하면 `blocked_extension` 테이블에 `user_id` 컬럼을 추가하는 방향으로 확장할 수 있다.
- **화이트리스트 방식 전환**: 현재는 블랙리스트(차단 목록) 방식이다. 허용할 확장자만 지정하는 화이트리스트 방식이 보안상 더 강하다. 테이블 구조 변경 없이 `type` 컬럼에 `ALLOWED` 값을 추가하는 방식으로 전환 가능하다.
- **캐시**: 현재는 업로드마다 DB에서 차단 목록을 조회한다. 트래픽이 많아지면 `@Cacheable`을 적용하고 정책 변경 시 evict하는 방식으로 개선할 수 있다.
