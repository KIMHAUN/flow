# 구현 및 설계 고려사항

---

# 1. 확장자 입력값 정규화

## 정책

커스텀 확장자는 저장 전에 아래 순서로 정규화한다.

1. trim()
2. 소문자 변환
3. 앞의 '.' 제거
4. 영문자/숫자만 허용
5. 길이 1~20자 검증

예시

```
.EXE -> exe
 Sh -> sh
```

## 이유

파일 시스템 및 운영체제는 일반적으로 확장자의 대소문자를 구분하지 않는다.

저장 시점에 정규화하면

- 중복 저장 방지
- 업로드 검사 로직 단순화
- 조회 시 일관성 유지

가 가능하다.

---

## DB 레벨 방어

애플리케이션에서 정규화를 수행하지만,
직접 DB 수정이나 버그 상황을 대비하여
LOWER(extension) 기반 Unique Index를 추가하였다.

```sql
CREATE UNIQUE INDEX uq_extension_lower
ON blocked_extension(LOWER(extension));
```

이는 애플리케이션 검증을 대체하는 것이 아니라
추가적인 방어 계층(defense in depth)으로 사용하였다.

# 2. 서버 검증 및 보안

## 서버 사이드 검증

클라이언트 검증은 브라우저에서 우회가 가능하므로
모든 입력 검증은 서버에서 수행한다.

검증 항목

- 중복 여부
- 길이
- 허용 문자
- 최대 개수
- 고정 확장자 여부

---

## Magic Number(File Signature)

현재 구현은 확장자 기반 검사만 수행한다.

실제 운영 환경에서는 Apache Tika 등을 이용한
파일 시그니처 검증을 함께 적용하는 것이 바람직하다.

이번 과제에서는

- 요구사항 범위
- 구현 복잡도

를 고려하여 제외하였다.

---

## MIME Type

Content-Type 헤더는 클라이언트가 임의로 변경할 수 있으므로
신뢰하지 않는다.

확장자 검사는 서버에서 직접 수행한다.

---

## 이중 확장자

예)

```
file.exe.txt
```

현재는 마지막 확장자(txt)를 기준으로 검사한다.

이는 대부분의 운영체제와 브라우저가 마지막 확장자를 기준으로
파일 형식을 판단하기 때문이다.

보안을 더욱 강화하려면
파일명 전체에서 위험 확장자 포함 여부를 검사하는 방식으로
확장할 수 있다.

---

## 확장자가 없는 파일

예)

```
Makefile
.env
```

현재는 허용한다.

과제의 차단 정책은 "확장자"를 기준으로 하므로
확장자가 없는 파일은 정책 적용 대상에서 제외하였다.

운영 환경에서는 조직 정책에 따라 별도 차단 규칙을 둘 수 있다.

---

## 파일 저장

원본 파일명을 그대로 저장하지 않는다.

예)

```
../../etc/passwd
```

와 같은 Path Traversal 공격을 방지하기 위해

```
UUID + 원래 확장자
```

형태로 저장한다.

예)

```
2f3ab2c1.pdf
```

원본 파일명은 응답에만 포함한다.

---

## 파일 크기 제한

Spring Multipart 설정으로 제한한다.

```properties
spring.servlet.multipart.max-file-size=10MB
spring.servlet.multipart.max-request-size=10MB
```

# 3. 정책 설계

## 고정 확장자

고정 확장자는 삭제할 수 없다.

또한 동일한 확장자를 커스텀으로 추가할 수도 없다.

중복 요청 시

```
DUPLICATE_EXTENSION
```

오류를 반환한다.

---

## 최대 200개

커스텀 확장자는 최대 200개까지 허용한다.

이는 과제 요구사항을 따른 정책이다.

---

## 최대 길이 20자

확장자는 최대 20자로 제한한다.

이는 과제 요구사항을 따른 정책이다.

---

## 감사 로그(Audit)

누가

- 추가
- 삭제

했는지 기록하는 감사 로그는
운영 환경에서는 중요한 기능이다.

이번 과제에서는 범위를 고려하여 구현하지 않았다.

추후

```
extension_audit_log
```

테이블을 추가하여 확장 가능하다.

---

# 4. 예외 처리

차단된 파일 업로드 시

```json
{
  "success": false,
  "code": "BLOCKED_EXTENSION",
  "message": "exe 확장자는 업로드가 차단되어 있습니다."
}
```

처럼

- 원인
- 오류 코드

를 함께 반환하여
클라이언트가 적절한 메시지를 표시할 수 있도록 하였다.

---

# 5. 트랜잭션

확장자 추가 및 삭제는

```
@Transactional
```

로 처리한다.

DB 저장이 실패하면
변경 사항은 모두 롤백된다.

---

# 6. 동시성

현재 구현에서는

```
200개 제한 확인
→ 저장
```

순으로 처리한다.

동시에 여러 요청이 들어오면
일시적으로 200개를 초과할 가능성이 있다.

실제 서비스에서는

- Optimistic Lock
- Pessimistic Lock
- SERIALIZABLE Transaction

등을 이용하여 보완할 수 있다.

이번 과제에서는 요구사항 범위를 고려하여 구현하지 않았다.

# 7. 운영 환경 고려

## 환경 변수

DB 접속 정보는

```
DB_URL
DB_USERNAME
DB_PASSWORD
```

환경 변수로 관리하였다.

민감한 정보는 GitHub에 포함하지 않는다.

---

## CORS

운영 환경에서는
프론트엔드(Render) 주소만 허용하였다.

개발 환경에서는 localhost를 사용한다.

환경 변수로 관리하여
환경별 설정을 분리하였다.

---

## Docker

백엔드는 Docker로 배포하였다.

동일한 실행 환경을 보장하고
로컬과 운영 환경의 차이를 최소화하기 위함이다.

---

## Logging

차단된 업로드는 GlobalExceptionHandler에서 처리한다.

운영 환경에서는

- 요청 IP
- 파일명
- 요청 시각

등을 함께 기록하여
감사 및 보안 분석에 활용할 수 있다.

---
